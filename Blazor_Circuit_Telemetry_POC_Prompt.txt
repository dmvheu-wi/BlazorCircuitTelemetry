You are implementing a new educational proof-of-concept in this GitHub repository:

https://github.com/Impesoft/POC_InnerWorkings

Your task is to create a .NET 10 Blazor Web App page that demonstrates and visualizes the internal behavior of an Interactive Server Blazor circuit.

Do not merely describe the solution. Inspect the repository, implement the feature completely, build it, resolve compilation errors, and report exactly what you changed.

# Primary goal

Create a page composed using static server-side rendering (static SSR) with two separate sibling interactive islands:

1. An Interactive Server component that contains controls and behaviors whose Blazor circuit activity is observable.
2. An Interactive WebAssembly telemetry terminal that observes, correlates, filters, and displays that activity without generating additional traffic on the Interactive Server circuit being observed.

Conceptually:

Static SSR page
├── Interactive Server playground — the observed subject
└── Interactive WebAssembly terminal — the observer

The feature is educational. It should make the relationship among browser events, SignalR transport traffic, Blazor circuits, server execution, render batches, JavaScript interop, and application-level actions understandable.

# Core architecture

Implement these distinct data paths:

## Browser transport observations

A JavaScript bootstrap observer must install before Blazor starts and observe the browser-side transport used for `/_blazor`.

It must:

- Wrap or instrument the browser WebSocket constructor before Blazor initializes.
- Only capture WebSocket connections whose URL targets the Blazor endpoint, normally `/_blazor`.
- Preserve native WebSocket behavior.
- Capture:
  - WebSocket construction.
  - Open.
  - Incoming messages.
  - Outgoing messages.
  - Error.
  - Close.
  - Close code.
  - Close reason.
  - Whether closure was clean.
  - URL.
  - Timestamp.
  - Sequence number.
  - Payload type.
  - Payload byte length.
  - A bounded hexadecimal preview for binary data.
  - A bounded textual preview for string data.
- Avoid consuming or altering Blob, ArrayBuffer, typed-array, or string payloads.
- Avoid logging secrets to the browser console by default.
- Keep a bounded browser-side ring buffer so startup events are retained before the WebAssembly terminal becomes interactive.
- Publish live entries to subscribers after the terminal starts.
- Be safely idempotent if installation is attempted more than once.

Use `autostart="false"` for `blazor.web.js` if required to guarantee observer installation before `Blazor.start()`.

Do not accidentally load Blazor twice.

## Server telemetry observations

Create a server-side telemetry service that receives and broadcasts structured events.

Use a bounded, non-blocking design. A slow telemetry consumer must never block or damage the observed Blazor circuit.

Suitable implementation options include:

- A singleton event publisher.
- Per-subscriber bounded channels.
- A fan-out broadcaster.
- Explicit removal of disconnected subscribers.

Do not use one shared ChannelReader that load-balances events among subscribers. Every connected telemetry terminal should see its own copy of events.

Expose server telemetry through a dedicated Server-Sent Events endpoint, for example:

```text
/_telemetry/events
```

Use SSE rather than a custom SignalR hub so the monitoring transport is clearly separate from `/_blazor`.

The endpoint must:

- Set `Content-Type: text/event-stream`.
- Disable caching.
- Stream serialized telemetry entries.
- Flush after events.
- Observe request cancellation.
- Remove disconnected subscribers.
- Send an occasional comment/heartbeat if necessary to keep proxies from closing idle streams.
- Avoid exposing telemetry in production accidentally.

Enable it only in Development or behind an explicit configuration option such as:

```json
{
  "BlazorTelemetry": {
    "Enabled": true
  }
}
```

Prefer both:
- Development environment.
- Explicit enabled setting.

Document the behavior clearly.

# Event ingestion in WebAssembly

The terminal has two sources.

## Source 1: Browser observer

Use JS interop to:

1. Read buffered startup events.
2. Subscribe to future browser transport events.
3. Deliver events to the WebAssembly component in batches.
4. Avoid one .NET interop call per tiny WebSocket frame where possible.
5. Flush batches on a short interval or when a bounded batch size is reached.
6. Unsubscribe and clean up on component disposal.

The observer should continue safely if the terminal component is temporarily absent.

## Source 2: SSE

The WebAssembly component should connect to the server SSE endpoint.

Because browser `EventSource` integration is convenient and robust, it is acceptable for JavaScript to own the EventSource and batch entries into the WebAssembly component.

Alternatively, use HttpClient streaming only if it is reliable in browser WebAssembly under the current .NET 10 environment.

The SSE client must:

- Reconnect naturally.
- Report connecting/open/error/closed states to the terminal.
- Avoid duplicate handlers after component rerender.
- Dispose cleanly.
- Avoid flooding .NET with individual callbacks; batch where sensible.

# Feedback-loop prevention

This requirement is critical.

The telemetry terminal must not use Interactive Server.

It must use Interactive WebAssembly so terminal rerenders happen locally.

Server telemetry must use SSE, not the observed Blazor SignalR connection.

Browser capture must observe only the actual Blazor `/_blazor` WebSocket.

Do not capture the SSE stream as a raw Blazor frame.

Do not create a custom SignalR hub for telemetry.

Do not send telemetry rows back through the Interactive Server circuit.

Do not call methods on the playground component from the telemetry component.

The two interactive islands should communicate only indirectly through:

- Browser observation.
- Server telemetry stream.
- Shared serializable contracts.

# Ring buffers and performance

All buffers must be bounded.

Suggested defaults:

- Browser startup/raw buffer: 2,000 entries.
- WebAssembly retained terminal entries: 5,000 entries total.
- Per-server-subscriber channel: 1,000 entries.
- Hex preview: first 128 bytes.
- Text preview: first 512 characters.
- UI rendering: virtualize long lists where useful.

Use `Virtualize<TItem>` if it works well for the terminal layout.

Avoid:

- Rebuilding all rows for every event.
- Excessive LINQ allocations in hot paths.
- Unbounded lists.
- Blocking locks.
- Blocking SSE writes across all subscribers.
- One JS interop call per frame if batching can prevent it.

Dropped events must be counted and shown rather than silently pretending capture is complete.

# Security and privacy
